Example: what the engine found

What you can do: read each problem by how many orders it touches, with the cause and the proof. Hours come last, as an estimate.

An engine run on synthetic data from an invented operator. This page reads engine/findings.json. The full report is the engine's report. Orders are counted in the records. Hours are an estimate with example assumptions, not measured at any operator.

Problems, by orders affected

What you can do: compare the problems by the measured count, and read the cause and the proof of each one. The order is the order of the counts, not of the codes.

R02 A catalog attribute is missing and filled in by hand

Orders affected (measured)
4,167 orders · measured
Estimate (example assumptions)
347.3 h

Cause

The technical sheet lacks a value the activation system needs, so a person fills it in by hand.

Proof

4,167 orders in the records. Strong evidence, confirmed. One case: ORD-1000.

hours = affected × manual_minutes / 60

What to do

Add the missing value to the offer's sheet, so nobody has to fill it in by hand.

R01 Activation fails and nobody retries

Orders affected (measured)
400 orders · measured
Estimate (example assumptions)
283.3 h

Cause

An activation failed and nobody tried it again within the window, so a person has to find the order and push it through by hand.

Proof

400 orders in the records. Strong evidence, confirmed. One case: ORD-1000.

hours = affected × (manual_minutes + wait_days × daily_followup_minutes) / 60

What to do

Retry a failed activation before a person has to go and find the order.

R05 The systems share no order number

Orders affected (measured)
300 orders · measured
Estimate (example assumptions)
225 h

Apart, not in the total: the links are inferred.

Cause

Some records do not carry their order's number, so a person has to work out which belong together.

Proof

300 orders in the records. Weak evidence, possible. One case: ORD-1550.

hours = incidents × investigation_minutes / 60

What to do

Carry the order number on every record, so nobody has to guess what belongs together.

R03 A timer expires and nobody acts

Orders affected (measured)
50 orders · measured
Estimate (example assumptions)
317 h

Cause

A process timer expired, nothing followed, and the order stays without service until a person finds it.

Proof

50 orders in the records. History evidence, confirmed. One case: ORD-1400.

hours = stuck × (manual_minutes + days_stuck × daily_followup_minutes) / 60

What to do

Give every timer an exit, so an expired order is never left without service.

R04 A retry creates a second service order

Orders affected (measured)
20 orders · measured
Estimate (example assumptions)
30 h

Cause

A second service order exists for the same line. When activation failed, the retry created a new order instead of reusing the first.

Proof

20 orders in the records. Strong evidence, confirmed. One case: ORD-1000.

hours = groups × cleanup_minutes / 60

What to do

Make the retry reuse the service order that already exists.

Estimate with example assumptions (R01 to R04)
