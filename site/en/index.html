Where do orders get stuck?
Flow Audit will find out.

What you can do here: follow an order from start to finish, see where it broke and how many hours were lost, and open a sample report.

An internet order crosses four or five systems and each one only sees its own part. Every system can say "my part went fine" while the customer still waits 69 hours. Flow Audit gathers what each system wrote down, rebuilds each order's journey and shows where the time goes.

Open-source technical demo (MIT), under construction. There is no commercial offer. Read the license.

How it works

One order, five systems, and what Flow Audit does with their notes

Order ORD-1005, from the made-up operator Ortelis. It should work in one hour. It worked at hour 69.

What you can do: press Next or Play. In steps 1 to 8 the order travels from system to system and each one writes down its part. In steps 9 to 12 Flow Audit gathers those notes, joins them, puts them in time order and finds the problems.

  • Sales channel
  • Product catalog CAT
  • Order manager OMS
  • Process orchestrator BPM
  • Activation system PROV
  • Flow Audit (outside the path)
  1. 0 h · Sales channel. Ana orders “SkyHome 200”, satellite internet, on the operator's website.
  2. +1 min · Product catalog. The catalog confirms the offer exists. But its technical sheet lacks one piece of data: the satellite's capacity profile.
  3. +3 min · Process orchestrator. Because the data is missing, the orchestrator opens a task for a person. An analyst checks the capacity by hand: 2 hours. Problem: A field is missing in the catalog and someone fills it in by hand R02.
  4. +2 h · Order manager. The order manager splits the order into technical work: a service order to activate the line and a work order to install the dish. The service order is born here.
  5. +3 h · Process orchestrator. A technician installs the dish at Ana's home. The installation ends well.
  6. +9 h · Activation system. The activation system tries to switch the service on. The satellite equipment does not answer and the attempt fails. Nobody schedules another attempt. Problem: Activation fails and nobody retries it R01.
  7. +69 h · Order manager. 60 hours later, Ana calls. Someone retries by hand, but the order manager creates a new service order for the same line instead of repeating the first one. A second service order is born. Problem: A retry creates a second service order R04.
  8. +69 h · Activation system. The second attempt works. Ana has internet 69 hours after ordering it.
The difference

The same order, told two ways

An order passes through five systems. Each system sees only its part.

Without Flow Audit

  • Five teams, five screens. Each sees that its part went well.
  • The 60 hours of inactivity appear in no system.
  • The audit is done with interviews and spreadsheets. The lost time is an opinion.
  • Two audits of the same operator reach different conclusions.

With Flow Audit

  • One journey per order, built from what each system already notes.
  • Each problem points to the order and the records that prove it.
  • Each figure shows its calculation in hours and the example minutes it uses, which can be changed in config.json.
  • With the same data, the result is always the same. It touches no system.

The five problems it looks for

Each problem has a code, R01 to R05. Figures are monthly, for an operator with 5,000 orders, using made-up data.
