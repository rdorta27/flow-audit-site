Design and components

Architecture

What you can do here: see the parts of Flow Audit, what it reads from each system, and what already exists and what is still design.

Flow Audit is a local-first command line tool: evidence goes in, a report comes out. Today it already reads data, joins it and detects one problem (R04); the report and the other four rules are still design.

Under construction · version 0.4.0. The components below are real files in the repository. Stages that do not exist yet say so.

Pipeline

Working today: ingestion (orders, service orders and activations, from a test API), reconstruction (joining records with a confidence level) and one rule (R04) with its cost. Still missing: wiring it all into one command (audit), the report and the other four rules. The demo report is a hand-made mock, not generated.

Components

Hexagonal layout (ADR 0002). The domain imports nothing outside src/domain/, and a test fails the build if that changes. An arrow means “depends on”.

domain/

The canonical model and the pure logic: events, orders, journeys, findings and impact, the join of records with its confidence, the classification of time (work, wait, gap) and rule R04. No I/O, no clock, no files. Today: all of that exists; the other four rules do not.

ports/

The four interfaces the rest of the engine depends on: EvidenceSource, CatalogSource, ReportRenderer and Clock. Today: the readers for orders, service orders and activations implement EvidenceSource; the file readers and the renderer are missing.

adapters/

The outside world. A clock, the export serializers and the readers. Today: clock/, export/ and ingest/ (readers for orders, service orders and activations over HTTP); report/ is empty.

app/

The runAudit() use case. It will tie ingestion, reconstruction, detection, quantification and rendering together, and owns no format. Today: a skeleton that counts records and returns no findings; rule R04 runs separately, in explain.

cli/

Argument parsing, help and exit codes. Five commands: audit, read, explain, stub and dataset. Today: read counts and joins the records, explain follows a duplicated order and audit exits with code 2 when there is no source.

dataset/

A deterministic generator with a fixed seed. It writes the synthetic Ortelis evidence: 5,000 orders in September 2026 and the impact rates. Today: it runs and the exports are byte-stable.

What runs today

Check

deno task check type-checks the CLI, the generator, the clock adapter and the tests. It passes.

Test

deno task test passes: dataset, serializers, the architecture and license boundaries, the skeleton, the test server, the three readers, the join and rule R04.

Audit

deno task audit does not run anything yet: it exits with code 2. What does run today: read (counts and joins records) and explain (one duplicated order, step by step).

Dataset

deno task dataset regenerates the 5,000 orders from a fixed seed. Two runs produce byte-identical exports.

Design

Core concept

Flow Audit is an audit tool. It reads the records of the systems an order passes through and rebuilds its path. For every loss it will work out the hours, the dollars and the evidence; today it does so for one (R04).

Physical analogy

Picture a parcel that crosses four warehouses. Each warehouse writes down only its own arrivals and departures.

Nobody knows where the parcel sat for three days. Flow Audit will put the four notebooks together. It will mark the warehouse where the parcel waited and add up the cost of that wait.

Technical mechanics

  • Ingestion. Will read the exports of the product catalog, order manager, process orchestrator and activation system.
  • Reconstruction. Joins the records of one order through the identifiers each system already carries (explicit link) and, only when they are missing, infers through another field, such as the terminal serial. Every link says how sure it is. The time window is not used yet.
  • Rules. Five rules will detect failures without retry, manual waits, expired timers, duplicates and a missing identifier.
  • Impact. Will multiply the affected orders by the minutes of work and by the loaded hourly cost.
  • Severity. Will derive the severity from the hours per month. Nobody will assign it by hand.
  • Report. Will generate one self-contained HTML file and a findings.json with the evidence of each finding.

Planned impact formula

  • Hours per month = affected orders × minutes of work per order ÷ 60
  • USD per month = hours per month × USD 45 per loaded hour
  • Example with the synthetic dataset (R02). 4,167 orders × 5 min ÷ 60 = 347 h. 347.25 h × USD 45 = USD 15,626.
