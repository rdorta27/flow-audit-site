Who uses it and when it helps

A short guide. Flow Audit is an open-source (MIT) technical demo under construction. See the engine's real report.

Who runs it

An analyst. They run the audit on the systems' exports and check what comes out.

Who reads it

The sponsor: the person who decides whether to fix things. They read the report and never touch the data.

When it helps most

With systems of different ages and vendors. With migrations, audited before and after. With configuration and process errors. With gaps between teams.

When it helps least

With one system that already follows the order from start to end. There are no joins to check.

Versus other ways to look

Monitoring tells you what is happening now; this checks what already happened, across systems. Process mining rebuilds the path from an event log; here you need that log and must match the order numbers. Interviews tell you what people believe; this shows what the data says. It does not replace them: they work together.

What to export

There is one list per system, with fields, format and period: the export table; the help page explains the rest: help page.

Minutes per task

Whoever audits supplies their own minutes per task in config.json. Without them, the hours are the example ones.

Where it runs

On the auditor's computer, from the command line. Nothing leaves that machine: data goes in and a folder with the report comes out.

Retention

The design keeps no copies: the engine holds no data between runs and writes only the output folder. Whoever audits decides how long to keep the exports and that folder.

What will it produce?

A report in one file

A page that opens in any browser, offline. It has a summary, the order path and the problems found.

Proof for each problem

Each problem names the order, the data that proves it and how its hours were calculated.

Repeatable results

With the same data, the audit always gives the same result.
